# Verdict without (much of) the LLM: ideas

Collected 2026-10-29. Post-parity (M9): anything here changes behaviour
relative to patent, so it would sit behind a flag (say
`--verdict floor|model|llm`) until it has proven itself.

Revisited the same day with measurements; see
[Revisited: measurements and a simple plan](#revisited-measurements-and-a-simple-plan)
at the end, which supersedes the plan here for the per-query verdict.

## Why

- **The LLM is the slowest step.** Fan-out takes a few seconds (15 s cap per
  source), ranking 300 texts takes 0.9 s, and the one live qwen3.5 run in M6
  took 10 s for the verdict. Through Ollama's `/v1` the same model thinks
  until it runs out of tokens (112 s, empty content), so the verdict falls
  back (todo.md, M9).
- **Three levels are coarse.** Open / Crowded / Saturated is fine as an exit
  code, but you can't rank ideas by it or compare areas.
- **A fast, deterministic score could be run over many ideas.** Over a
  harvested index it could find underserved areas, without an LLM call per
  query.

## What the verdict does today

| step | where | what |
|---|---|---|
| relevance gate | `internal/pipeline/pipeline.go:161` | best similarity < 0.35 → "nothing relevant", no LLM |
| floor | `verdict/verdict.go:178` | over the top 50: ≥ 5 matches ≥ 0.60 → Saturated; ≥ 2 ≥ 0.55 or 1 ≥ 0.70 → Crowded |
| LLM | `verdict/assess.go:324`, prompt in `verdict/verdict.go:49` | prompt with the top 15 (sim, popularity, age, URL); returns level, headline, gaps |
| guards | `verdict/assess.go:227` (`parseVerdict`) | `level = max(model, floor)`; absence and no-match headlines replaced; gaps that claim absence or name a top-10 match dropped |

Two things follow:

1. **The LLM can only raise the level, never lower it.** Its prompt tells it
   to discount tangential matches, but the floor has already counted them.
   So the LLM changes the level only by upgrading it; what it adds beyond
   that is the headline and the gaps, and the guards often swap the headline
   for the data headline anyway.
2. **The floor ignores most of the signal it has**: popularity, freshness,
   which sources failed, and how specific the idea is. It counts matches
   above three cosine thresholds of a symmetric sentence-similarity model
   (all-MiniLM-L6-v2), thresholds patent calibrated on that model's values;
   patent's repository has no record of how.

From the parity runs (`2026-10-26-parity.md`):

- *django admin theme with dark mode*: Open. The obvious candidates live on
  PyPI, which is selected and never reached.
- *cloud-native secret manager for k8s clusters*: Crowded, in a space with
  several well-known projects.
- *CLI tool that kills a process on a given port*: Open with
  `--keyword-only`, Saturated with embeddings; the keyword fraction is
  measured against thresholds calibrated on cosines (a patent quirk).

The asymmetry behind all this: a false Open breaks the integrity principle,
while a false Saturated is only useless. The floor is built to avoid the
first, and it gets there by handing out the second for any generic idea.
Underserved-area detection needs the useless side fixed too.

## Reframing: three sub-problems

```
            per match                    per idea                 text
idea ─▶ (a) does m implement q? ─▶ (b) how crowded is it? ─▶ (c) headline, gaps
        p_i ∈ [0,1]                  score S, level, confidence     (LLM, optional)
```

- **(a) is pairwise relevance**: "is this match an implementation of the
  idea?", not "is it about the same topic?". The cosine answers the second
  question. Cross-encoders, NLI models and rerankers fit here.
- **(b) is a small classic model** over a dozen features: thresholds, ordinal
  regression, a shallow tree.
- **(c) is the only part that needs a generative model**, and it could be
  optional: on demand, or computed after the level is already shown.

A natural score for (b) is an **expected number of established
implementations**:

```
S = Σ_i p_i · a_i · f_i
```

where `p_i` is (a)'s probability, `a_i` an adoption weight (log popularity,
normalised per source), and `f_i` an optional freshness weight. The levels
become cut points on S. S is continuous, so ideas and areas can be ranked by
it, which is what underserved-area detection needs.

## (a) Per-match scorers

| scorer | what | cost per idea (50 matches) | in pure Go? | notes |
|---|---|---|---|---|
| MiniLM cosine (today) | symmetric sentence similarity | ~0.15 s | yes | rewards a shared topic, not the specific feature |
| asymmetric bi-encoder (bge-small-en-v1.5, e5-small-v2, Qwen3-Embedding-0.6B) | trained for query → document retrieval, with a query instruction or prefix | similar (small ones) | bge/e5 small: mostly; BERT-shaped, 384 dims, but 12 layers and CLS pooling for bge | needs new thresholds; changes the ranking too |
| cross-encoder `cross-encoder/ms-marco-MiniLM-L-6-v2` | idea and match in one pass, one relevance logit | ~0.15–0.3 s (estimate: 50 pairs vs 300 texts in 0.9 s) | yes, small change: same shape as all-MiniLM-L6-v2 (6 layers, 384 hidden, BERT vocab); needs `[CLS] q [SEP] d [SEP]` with token type 1 on the second segment (`internal/minilm` loads both type rows, uses row 0), plus BERT pooler and a 1-logit head | trained on web search passages, not "is an implementation of"; logits need calibrating (Platt) |
| NLI cross-encoder (zero-shot) | premise: match text; hypothesis: "This software is {idea}"; entailment probability | like the cross-encoder | MiniLM-based ones: yes; DeBERTa ones need a SentencePiece tokenizer | "entails" is closer to "implements" than "relevant" is |
| instructed reranker (Qwen3-Reranker-0.6B, bge-reranker-v2-m3) | P("yes") for "does this software implement the idea?", with an instruction we write | seconds on CPU, less on GPU | no: llama.cpp server or Ollama | one token per pair, no generation; the homelab already serves Qwen3-Reranker |
| small LLM as a judge | per match, one yes/no token with logprobs; or all 15 in one prompt, answer as a bitmask | 1–3 s (guess) | no | a middle ground; needs a server that returns logprobs (llama.cpp's `n_probs`) |
| lexical, IDF-weighted | coverage of the idea's rare terms ("jq-style", "live filtering") in name + description | µs | yes | catches the specific feature that embeddings smooth over; IDF from the result set, later from the index |
| facets | split the idea into 2–4 facets (form: cli/library/extension; object: port, k8s logs; feature: live filter); score each, combine with min | n × the scorer | yes with any of the above | the facet the strong matches miss is a **gap**, found without an LLM |

On the "joint encoding didn't help" result: possible reasons, to check
rather than assume:

- ms-marco relevance is not "implements";
- it was judged on ranking, where the cosine is already fine, rather than on
  the level;
- the raw logits were compared against cosine thresholds without
  calibration;
- there were no labels, so nothing could show it helping.

## (b) Aggregation into a level

Features per idea:

- similarity shape: max, top-k mean, counts above several thresholds,
  Σ p_i (expected number of implementations);
- adoption: Σ p_i · log(1 + pop_i), with popularity normalised per source
  (npm's 0–1e6, GitHub stars and crates.io downloads aren't comparable raw);
- freshness: share of relevant matches stale (⚑), weighted by adoption;
- spread: number of distinct sources with a relevant match;
- coverage: sources reached / selected; which big registry failed (PyPI
  always does);
- specificity: content tokens, mean IDF of the idea's terms, how close the
  idea's embedding is to generic ideas ("a java spring boot service");
- result-set size before ranking.

Models, smallest first:

1. **Refit the floor**: same rule form, thresholds by grid search against
   labels. Interpretable, the smallest change.
2. **Ordinal logistic regression** (proportional odds): 10–15 coefficients,
   trained offline, shipped as Go constants.
3. **A depth-3 decision tree**, printed as if/else.
4. **Gradient boosting with monotone constraints**, only if there are
   thousands of labelled ideas.

With tens to hundreds of labelled ideas, 2 or 3 with leave-one-out
cross-validation.

Integrity constraints:

- The data floor stays a hard lower bound: a learned model may raise the
  level, as the LLM may today, never lower it below the floor.
- Monotone in evidence: more or stronger relevant matches never lower S
  (positive coefficients on the supply features, or monotone constraints).
- Coverage lowers **confidence**, not the level. An Open over 2 of 6 reached
  sources becomes "Open, low coverage" (patent's `confidence` idea), never a
  lower level.
- The headline stays the data headline unless (c) runs; the guards stay.

## Labels

Nothing works without them, and today there are none beyond patent's own
outputs.

- **Gold set**, hand-labelled: start with the 33 parity ideas (the 22
  differential ones are among them), grow to ~100. Per idea a level; per
  top-15 match "implements / partial / no".
- **LLM as teacher**: a strong model labels pairs offline (100 ideas × 15 =
  1500 pairs), with a human-checked sample. The small model learns to imitate
  the teacher, so the 10 s per query moves into a one-off batch job. This is
  the "system 2 trains system 1" idea.
- **Synthetic positives**: a package's own description, paraphrased, as the
  idea. The package itself must come out as "implements" and the level at
  least Crowded. This is a recall check for (a).
- **Natural labels**:
  - awesome-lists: a category heading plus its entries is an idea with its
    implementations;
  - "Ask HN: is there a tool that …" threads: the question is the idea, the
    answers name tools;
  - GitHub topic counts.
- **Temporal labels** (needs the harvested index with creation dates; the
  crates.io dump has `created_at`): compute S on the index as of time t,
  count the packages that arrive in the next 12 months. This labels
  "underserved, then filled" without anyone judging.

Evaluation:

- confusion matrix, with false Open as the costliest cell;
- quadratic weighted kappa on 0/1/2;
- pair-level AUC or NDCG@10 for (a);
- milliseconds per idea.

Replay every fan-out through `internal/httprec`, so every scorer sees the
same matches.

## Underserved areas

- **Score many ideas.** With S and a confidence, generate or collect ideas and
  sort them by low S. The output is still scoped: "nothing close turned up in
  the sources checked", never "nobody has built this".
- **Map an index instead of answering queries.** Cluster the harvested
  packages' embeddings (k-means or HDBSCAN over MiniLM vectors, or registry
  keywords and topics). Per cluster, compare:
  - supply: package count, maintained count, adoption;
  - demand: download growth, HN mentions, "is there a tool" questions.

  High demand with little maintained supply is a candidate.
- **Abandonware areas.** High adoption, mostly stale. patent's prompt already
  says "room for a maintained alternative"; this makes it a number:
  adoption-weighted stale share.
- **Cross-ecosystem gaps.** A function cluster that is Saturated on npm and
  PyPI but empty on crates.io, Go or Hex is a port opportunity. Needs
  identity linking (M9, "normalise repository URLs"), so that bindings and
  ports of one project don't count as independent supply. Normalise per
  ecosystem: registries differ by orders of magnitude in size.
- **Facet gaps.** Per query, the facet least covered by the strong matches;
  the algorithmic version of the LLM's `gaps`.

## If the LLM stays

- **Cascade**: system 1 first, the LLM only near a cut point (uncertain) or
  when gaps are wanted.
- **Show system 1 immediately** in the TUI, and let the LLM's headline and gaps
  arrive later.
- **Level from system 1, text from the LLM**, so the LLM's output can't move
  the exit code.
- Cheaper calls:
  - Ollama's `format` with a JSON schema;
  - a smaller `num_predict`;
  - `keep_alive`, so the model stays loaded;
  - measure cold and warm separately (the 10 s run didn't say which it was).

## Open questions

- Keep three levels, or report S plus a confidence and derive the level for
  the exit code only?
- Is the floor still needed if (a) is well calibrated? Probably yes, as a
  cheap, auditable invariant.
- Who labels the gold set, and how much disagreement between two labellers
  is normal? Crowded vs Saturated is fuzzy, so measure it before fitting.
- Is idea specificity a separate output ("too generic to judge") rather than a
  feature? "a java spring boot service" deserves that answer more than
  "Saturated".

## Revisited: measurements and a simple plan

The plan above is mostly about a continuous score S for **underserved
areas**. The problem at hand is narrower: a per-query verdict that is fast,
deterministic and doesn't need an LLM server. The two had been treated as one
problem. The second needs none of the scorers, labels or models above.

### What the LLM does, measured

qwen3.5:9b (Q4_K_M) on local Ollama, CPU only (8 cores, `size_vram: 0`),
model warm, silt's options (`think: false`, temperature 0, `num_predict`
512), prompt from `verdict.BuildPrompt` over the recorded matches in
`testdata/embeddings/differential.jsonl`. The LLM can only raise the level,
so besides two controls only the ideas below Saturated were run (#: line in
the file).

| # | idea | floor | LLM | final today | s |
|---|---|---|---|---|---|
| 2 | CLI tool that kills a process on a given port | Saturated | Saturated | Saturated | 83 |
| 5 | a vector database for embeddings | Crowded | Saturated | Saturated | 182 |
| 7 | an ide plugin that highlights spelling mistakes in code comments | Crowded | Saturated | Saturated | 188 |
| 8 | a python pandas data pipeline | Open | Open | Open | 189 |
| 9 | a typescript react frontend component | Crowded | Open | Crowded | 186 |
| 20 | a nix flake for building containers | Crowded | Saturated | Saturated | 187 |
| 21 | 端口杀手命令行工具 | Open | Open | Open | 192 |
| 22 | a terminal ui for exploring large json … fuzzy search | Open | Open | Open | 181 |

- **Time.** Prefill dominates: 1.6–1.8k prompt tokens at 11–30 tok/s
  (54–167 s), then 110–130 tokens at 4.4 tok/s (25–28 s). `num_predict`,
  `format` and `keep_alive` don't touch the prefill; only a GPU or a much
  shorter prompt would. The 10 s of M6 was presumably on a GPU; not recorded.
- **Timeout.** 7 of 8 take longer than the client's 120 s (`llm/llm.go:29`).
  A timeout is an `LLMUnreachableError`, so `Assess` retries once and the
  pipeline then falls back. By the code path (not run end to end), a default
  run on this machine spends ~240 s on the LLM and then reports Open.
- **Level.** 3 raises out of 7 possible: two plausible (5, 20), one over-call
  (7: one match ≥ 0.60, where the prompt's own rule asks for 5+). None of the
  three false Opens (8, 21, 22) was fixed.
- **Headline.** All three raised verdicts keep the model's headline, and all
  three cite "strong matches (similarity >= 0.60)" that aren't there: #5 calls
  Milvus (0.49) one, and #7 has one match ≥ 0.60 but claims several. The
  guards replace the headline in 8, 9 and 21.
- **Gaps.** 15 over 8 ideas: 4 specific (JSDoc/KDoc comment standards; a
  flake template for multi-stage builds; containerd shims; port-kill in
  network diagnostics), 7 generic ("a niche use-case", "better performance",
  "a different runtime"), 4 restating the idea. #22's two gaps describe jnv,
  jqp and ijq, which exist but weren't retrieved.

### What happens without an LLM today

An LLM that is unreachable, times out or returns garbage gives a **bare
Open, exit 0**, whatever the matches show
(`internal/pipeline/pipeline.go:250`, pinned by
`TestRunFallsBackToSearchOnlyVerdictWhenTheLLMFails`). That is patent's
behaviour. So the default configuration on a machine without a fast LLM
produces the costliest cell, a false Open, even for "kubernetes log viewer".
`--fast` doesn't have this problem: it uses the floor.

### Plan

Deterministic, no new model, no labels:

1. **The data verdict is the default.** The LLM runs only when asked for (a
   flag such as `--llm`, or a config key); `--fast` stays accepted. The
   default run is then instant, local, and nothing leaves the machine.
2. **An LLM that fails falls back to `FromData`**, never to a bare Open.
3. **With the LLM on, it contributes gaps only.** Level and headline come
   from `FromData`, so the exit code is the same with or without an LLM, and
   the wrong counts in the model's headline don't reach the user. Done in
   `pipeline.Run` after `Assess`, so `verdict`'s parity tests stay as they
   are. The gap guards stay.

Optional polish of the data headline (prototyped on the 22 runs):

4. Name the closest matches, packages and repos before HN posts: "Saturated —
   9 closely-related tools turned up in the sources checked; closest:
   kill-port (npm), fuckport (crates.io), kill-port-process (npm)."
5. On Open, name the sources not reached ("Not reached: PyPI"), the todo
   item from M9.
6. If most of the idea's letters aren't Latin, say that the similarity model
   reads English only and suggest rephrasing (catches 21 and the Japanese
   parity idea).

4–6 change `FromData`'s headline, so `TestFromDataMatchesPatent` and the
differential test need new expectations and a line in the deviations table.

Not part of the verdict:

- **Recall for long ideas** (#22) is a retrieval problem: the keywords sent
  to registries and the cosine against a many-facet idea. It belongs with the
  search, not the verdict.
- **S, the per-match scorers, labels and E1–E6** stay the plan for
  underserved areas over a harvested index.
